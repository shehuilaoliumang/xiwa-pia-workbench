## 2. 发现与处理

| 编号 | v0.3 发现 | 可能造成的问题 | v0.4 处理 |
|---|---|---|---|
| R-01 | 第 4 节“应用才改画面”未明确区分即时开始/暂停/速度/定位；预览改方向与实际上屏换方向混用 | 每次暂停都要再点应用，或改预览就中断直播 | 第 4.1 节区分内容预览与即时播控；只有应用画幅时才暂停和重排 |
| R-02 | 第 7 节提出服务端持久化、浏览器滚动和轮询，但缺少位置回传与重复命令规则 | 恢复不到原位置，或轮询反复把页面拉回旧位置 | 暂停/定位时及时保存，自动滚动节流保存检查点；使用状态版本或命令标识处理新动作，不逐帧写库 |
| R-03 | 已要求重启暂停，但未明确仅刷新展示窗口、换本或原段落被删除时的行为 | 刷新后意外播放、不同页面状态不一致、跳到错误位置 | 展示刷新/服务重启恢复快照与最近语义位置并暂停；操作页刷新不干扰直播；换本从头，同篇保留有效定位，失效时回起点并提示 |
| R-04 | 升级预留表把“创建空数据库”放入“此次及首版不提前实现”列 | 可能误解为首版也不能初始化 SQLite | 明确首版正常建立核心数据库，仅不为未启动视频功能预先创建空媒体库或服务 |

另补强两项实施条件：

- 原计划验收只说“14 个条目能打开正文”，现明确核对 14 篇、69 页及全部角色/表演提示、必要插图和源页映射，避免只检查入口。
- 将 Python 主语言写清，增加项目独立运行环境要求；抖音采集方式在第一个可用展示页出现后尽早验证，不等到所有功能完成才检查。

以上为保持现有用户需求一致的默认实现建议，没有把视频、多人控制、公网服务或 Sites 发布加入首版。

## 3. 未发现冲突的部分

| 检查点 | 结论 |
|---|---|
| Python 与 Flask/Jinja/SQLite | 同一 Python 单体技术方案中的不同组成，彼此不冲突 |
| 前后端不分离与少量 JavaScript | 页面、服务与资源在同一项目运行，浏览器交互代码不构成独立前端部署 |
| 原六类与动态分类管理 | 原六类是初始数据；当前分类可维护，原 PPT 分类另存用于追溯 |
| 分类隐藏/删除与已上屏快照 | 资料和预览更新；当前展示保留至再次应用，引用资源需继续有效 |
| 首版手动定位与未来视频台词 | 首版正文定位独立可用；视频区、字幕单元及媒体同步仍是后续功能 |
| 手机尺寸适配与只开放本机 | 首版可验证手机宽度布局，无需因此开放局域网或公网 |
| 原稿疑点与内容导入 | 疑点按原页序、原文和原备注保留，来源核查机制明确，不阻碍初始导入 |
