# 上游同步流程（xiwa main → 通用模板）

> ## 同步范围（硬规则，先读这条）
>
> - **只同步稳定版 `main`**，并且**必须等项目所有者明确说出"同步"之后**才动手。
> - **实验分支（`feature/*`）一律不同步**，无论它包含多少新功能、看起来多完整。
>   实验分支是作者自己的试作，可能随时重做或丢弃；把它并进模板等于替作者做了决定。
> - **没有收到同步指示时，保持 `template` 分支原样**，不主动拉取、不合并、不"顺手"移植。
> - 收到指示后的动作范围：拉取 `main` → 盘点差异 → 按功能移植 → 跑测试与残留扫描 →
>   给出变更清单与需人工拍板项 → 经确认后提交并推送。

本文件说明：**当 GitHub 上的 `xiwa-pia-workbench`（main 分支）有功能更新时，如何把功能同步进本通用模板。**

结论先说：**可以做到**，而且不是凭记忆手改，而是一套可重复、可验证的流程。但它是**按功能移植**，不是直接 `git merge` —— 原因见第 1 节。

---

## 1. 为什么不能直接 merge

| | 上游 `xiwa-pia-workbench` | 本地通用模板 |
| --- | --- | --- |
| 命名 | 喜娃、微PIA、抖音号 84984989506 | 内容管理工作台 / 内容编辑器 |
| 术语 | 剧本、分类、播控台、独立展示器 | 条目、分组、展示控制、展示窗口 |
| 结构 | `喜娃剧本粉丝编辑器/` | `内容编辑器/` |
| 标识 | `xiwa-workbench`、`xiwa-script-package` | `content-workbench`、`content-package` |
| 内部命名空间 | `pia-media-*`、`piaDesktop` | `wb-media-*`、`wbDesktop` |

两边已分叉 122 个文件。直接 merge 会把品牌名整套灌回来，并在改过的文件上大量冲突。
所以采用**按功能移植**。

---

## 2. 分支约定

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 与上游保持一致 | **只在同步时快进**，永不在此提交模板改动 |
| `template` | 通用模板主线 | 日常工作分支；同步结果提交到这里 |

`main` 停在 `3d955ae`（= 上游同步基线）。以后每同步一次，把它快进到新的上游提交，
下次就能用「`main`..`origin/main`」精确算出「这次上游改了什么」。

---

## 3. 每次同步的六个步骤

### 步骤 1 · 备份当前模板

```powershell
cd <你的项目目录>
git tag template-before-sync-(Get-Date -Format yyyyMMdd)
```

### 步骤 2 · 拉取上游

```powershell
git fetch origin main
```

> 本仓库已设置 `http.sslBackend=openssl`。这台机器的 Windows TLS（schannel）拉 GitHub 会直接失败
> （`SEC_E_NO_CREDENTIALS`），必须用 openssl 后端；同时限速参数已设，避免慢链路被误判为卡死。
> GitHub 约 70 KB/s，仓库约 97 MB，**首次全量拉取可能需要 20–30 分钟**。

### 步骤 3 · 盘点上游改了什么

```powershell
git log --oneline main..origin/main --name-status
```

产出：新增(A)/修改(M)/删除(D) 文件清单。**先给用户看这份清单，确认哪些是功能、哪些只是文案。**

### 步骤 4 · 分类移植

| 情况 | 处理方式 |
| --- | --- |
| **上游新增的文件** | 复制过来，再套映射表去品牌 |
| **上游修改、且模板也改过的文件** | **逐段判断**：功能改动移植，品牌/术语文案丢弃（这是唯一需要人工判断的部分） |
| **上游修改、模板没改过的文件** | 直接取上游版本 |
| **上游删除的文件** | 同步删除 |
| **上游改写的文档** | 取上游内容后用通用术语重写标题与措辞 |

映射表位置（本机 `.backup/`，不进版本库）：

| 文件 | 内容 |
| --- | --- |
| `.backup/legacy_mapping.json` | 第一轮：品牌词、标识符、术语泛化 |
| `.backup/legacy_mapping2.json` | 裸品牌字、测试夹具角色名 |
| `.backup/legacy_mapping3.json` | 内部命名空间 `pia-` → `wb-` |

用法：

```powershell
runtime\python.exe -X utf8 tools\templating.py --mapping .backup\legacy_mapping.json --dry-run
```

> ⚠️ **换机器请把 `.backup/` 一并带走**，否则映射表只有历史提交里才有。
> 注意 `legacy_mapping2.json` 里的裸字规则**不能**再整体跑一遍（会误伤正常中文）；
> 它只用于处理明确的新增品牌文案，一律先 `--dry-run` 看命中。

### 步骤 5 · 验证

```powershell
# 全量单测（当前基线 139 项）
runtime\python.exe -X utf8 -m unittest discover -s tests -p "test_*.py"

# 关键页面冒烟（隔离数据目录，不碰 instance/）
runtime\python.exe -X utf8 run.py --no-browser --port 8799 --data-dir .qa-sync

# 品牌残留扫描（白名单外必须为 0）
runtime\python.exe -X utf8 tools\templating.py --patterns 喜娃 xiwa 微PIA 微pia 84984989506 抖音 直播伴侣 `
  --exclude docs/模板改造-变更清单.md --exclude docs/模板改造-残留清单.md --exclude docs/模板改造-测试与验收记录.md
```

### 步骤 6 · 出报告

给用户三样东西：

1. **上游改动清单**（哪些文件、哪些功能）
2. **本地移植清单**（逐文件改了什么）
3. **需人工拍板清单** —— 例如上游也重写了同一段代码时的取舍

## 4. 方案 3：一套代码 + 两份配置档案

品牌信息已全部抽进 `config/template.json`。因此**喜娃版和通用版不再是两套代码**：

```
config/template.json   ← 通用版（当前生效）
config/xiwa.json       ← 喜娃版（她的名字、抖音号、甜本/苦本、原始种子数据）
```

> 待做：`config/xiwa.json` 与切换脚本尚未创建。等上游有了新功能、需要同时产出两个版本时再补，
> 避免现在多维护一份无人使用的配置。

产出两个版本的思路：

```powershell
# 通用版
runtime\python.exe -X utf8 tools\customize.py --non-interactive --yes --name ... 
# 喜娃版（用她的配置档案覆盖 config/template.json 后打包）
```

## 5. 我能做到的 / 做不到的

**能**

- 机械改名、术语统一、标识符与格式对齐
- 套映射表批量处理新代码，并给出逐文件变更清单
- 跑单测、页面冒烟、残留扫描，出验收记录
- 判断哪些改动是纯文案（可丢弃）、哪些是功能（必须移植）

**做不到 / 需要你定**

- **新功能在你的领域里该叫什么名字** —— 我不会替你猜
- **上游重写了同一个文件时的取舍** —— 需要你拍板保留哪边
- 网络与凭据：`git push` 需要你的 GitHub 权限；GitHub 若连不上，只能等网络恢复

## 6. 命令备忘

```powershell
cd <你的项目目录>

# 看当前状态
git branch -v
git log --oneline -3 template
git status --short | Measure-Object -Line

# 同步（网络恢复后）
git fetch origin main
git log --oneline main..origin/main --name-status

# 同步完把基线推进
git checkout main && git merge --ff-only origin/main && git checkout template
```
